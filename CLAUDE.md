# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

`rnd-ta` is a co-op stealth game: a group of 2–4 players, aliens flying a saucer, land at a house and try to steal the pets living there. This repo **is** the Unity project (no sub-projects) — so this file is both the convention doc and the rulebook. Read it before touching code, scenes, or assets.

## The game

- **Hub** — the flying saucer the players start from and return to.
- **Level** — the house they raid.
- **Pets** — three of them, distinguished by size: **Dog** (big), **Kitty** (medium), **Parrot** (small). They try to run away and hide from the players.
- **Old Man** — an angry old man with a shotgun who lives in the house. If he sees a player, that player dies instantly.
- **Win condition** — carry every animal into the saucer and fly away.

Use these names in code and asset names. `Dog` / `Kitty` / `Parrot` / `Old Man` are already the prefab names in `Assets/_Game/Content/Level/Characters/`; the hub is `UFO.prefab` and the level is the scene `Assets/_Game/Content/Scenes/Level.unity`.

**Design docs (Russian).** `DD.md` holds the concept — treat it as the authoritative statement of the design. `MECHANICS.md` is the buildable breakdown: tunable values, per-mechanic authority for the coming multiplayer pass, and Must/Should/Defer tiers. Read `MECHANICS.md` before writing gameplay code, and take numbers from its tunables table rather than inventing them. `NETCODE.md` (added 2026-08-12) is the third: the map of **which mechanic is replicated by which class through which channel** — read it before touching anything networked, and update it in the same commit when a channel changes. It carries no tunables and no history; the reasons and the measured failures stay here. There are three read-only reviewer agents, and they do not overlap: `.claude/agents/gamemechanics-validator.md` audits the **docs** against the concept, the 5-hour budget and this project's Unity constraints; `.claude/agents/ai-behaviour-auditor.md` audits the **AI code** (`Code/AI`, `Code/Pets`, `Code/OldMan` and their wiring) against `MECHANICS.md` sections 2/4/5, the rules below, and Unity lifecycle correctness; `.claude/agents/netcode-readiness-auditor.md` (added 2026-08-04) audits **all** of `Code/` for what a multiplayer pass would cost — ownership, authority seams, determinism, and the criteria a networking library would have to meet — and is deliberately library-agnostic: it never picks one. All three report `BLOCKER` / `ISSUE` / `NIT` findings; the intended loop for the two auditors is run → fix → re-run until only NITs remain.

**Current state (2026-08-12):** greybox stage; every gameplay block in `MECHANICS.md` is built — movement, noise, doors, carrying, the animals, Old Man, death and the win/loss check — and so is the netcode. The meta cycle of `DD.md` has its first leg: the session now runs `Menu → Hub → Level → Hub`, with the hub a walkable but empty scene. Art and audio are not done. The whole loop was driven in Play mode on 2026-08-12 **in one process, host only** — menu → hub → level → hub → level again, including the end panel and its statistics; **nothing has been run on two machines**, so joining, late join and the client's half of every transition are still unmeasured. There is one level (`Level.unity`), built out of asset-store packs. The house is `HouseOneFloor.prefab` (single storey; `HouseTwoFloor.prefab` also exists but is not in the scene) and it ships with the pack's modular colliders. **NavMesh is baked**: one `NavMeshSurface` on the scene object `Navigation` (`Collect Objects: All`, `Include Layers: WalkingArea + BlockedArea`, `Use Geometry: Physics Colliders`), data in `Assets/_Game/Content/Scenes/Level/NavMesh-Navigation.asset`. Spawn points live under the scene root `Spawns` (`PlayerSpawn` ×4 in the yard, `PetSpawn` ×8 and `OldmanSpawn` ×3 in the house); each marker prefab carries a `SpawnPoint` component naming its kind, so a new marker dropped into the level is picked up without rewiring anything.

**The beam** is the scene root `Beam`, standing on the players' spawn point at `(-7, 0, -5.5)` — the saucer sits exactly above it. `BeamZone` on it is the rule — a **radius test, not a trigger collider** (see `MECHANICS.md` 4.5); the radius is a tunable that has been retuned more than once, so read it off the component rather than trusting any number quoted in prose, and its children are only the look of it: `BeamColumn`, a collider-less cylinder with an additive `Beam-MAT` running from `y = -0.3` to `y = 10.5`, and `BeamSpot`, a spot light in the hull's recess. **Nothing in this scene may sit exactly on `y = 0`**: the lawn is a zero-thickness `Plane` at exactly that height, and a coplanar face z-fights with it — that is why the column's bottom cap is buried rather than flush. The saucer itself bobs and spins (`UfoDrift` on the scene's `UFO`), which is why the column's top is buried `0.33 m` inside the hull. `LevelGoal` next to `Bootstrapper` owns the outcome: an animal released inside the beam is handed over, and the raid is won once all of them are aboard and every living player stands in the beam. Since 2026-08-04 the loss branch is reachable too — "living" means `PlayerLife.IsDead` is false, not `activeInHierarchy`, because a shot player stays in the scene as a spectator camera. `PlayerLife` is also what puts a dead carrier's animal down, and it routes that through `LevelGoal.ReleaseCarried` rather than `Pet.Release`, so being shot **inside** the beam still counts the animal as delivered (`MECHANICS.md` 3.7).

**There are three entry points and they are different things** (the third added 2026-08-12). `Assets/_Game/Code/App/Bootstrapper.cs` is the **application's**: it sits in `Loading.unity`, instantiates the persistent `Session` prefab and loads `Menu`. `Assets/_Game/Code/Hub/HubBootstrapper.cs` is the **hub's** and `Assets/_Game/Code/LevelBootstrapper.cs` is the **level's** — both are the scene root named `Bootstrapper` in their own scene, and both die with it. The session layer lives in `Code/App/`: `RaidSession` (host/join/leave, `GoToHub` and `StartRaid(sceneName)` through FishNet's own `SceneManager`, and the closed door on late join) plus `LobbyRoster` (a spawned `NetworkObject` holding the replicated player list). Their prefabs are `Assets/_Game/Content/Shared/Session.prefab` and `LobbyRoster.prefab`; FishNet keeps its own generated registry at `Assets/DefaultPrefabObjects.asset` and populates it itself — do not hand-edit it. **`LobbyRoster.prefab` is the project's only `IsGlobal` object** (set 2026-08-12): the session now lives in the hub, so the roster has to outlive the menu scene, and FishNet moves a global non-scene object into `DontDestroyOnLoad` in `NetworkObject.TryStartDeactivation`. The menu UI (`Code/UI/MenuView.cs`, `LoadingScreen.cs`) is the user's own and is wired to that layer, not to FishNet directly. Inside the lobby panel there are two **mutually exclusive** steps — Options (Host/Connect) → Address (`ip:port`, port optional) — switched by `SetActive`; the old third step, the player list with its ready flags, went away when Host/Connect started leading straight into the hub, and `MenuView` keeps a reference to that panel for the sole purpose of switching it off. `PlayerLobbyUI.cs` and `Content/Lobby/PlayerLobby.prefab` survive it, unused, for the hub's own list. **The starting panel is chosen in `Awake`, never by the alphas saved in the scene** — that is what made the game open on the lobby, and until the first switch every panel still blocked raycasts, so an invisible one ate the clicks. A failed connection is **not** reported promptly: Tugboat is LiteNetLib with `MaxConnectAttempts = 10`, so "not found" takes about five seconds and is indistinguishable from a later disconnect — `RaidSession.IsConnecting` is what tells them apart, and there is an `8 s` backstop. **A raid must never outlive its connection**, and the disconnect callback alone is not enough to guarantee that: it is one link in a chain FishNet runs while it is tearing every spawned object down, and a client left in a level with no host has also lost its avatar — and with it the camera, the HUD and the only way out. So `RaidSession.Update` watches `_inSession` against "are we still connected to anything" every frame and returns to the menu on its own (added 2026-08-05, after a host quitting the build left a client stranded). **That backstop is worthless without the one below it**: `Tugboat` leaves LiteNetLib's `DisconnectTimeout` at its own `MAX_TIMEOUT_SECONDS`, **1800 seconds**, so a peer that stops answering *without saying goodbye* — a build killed rather than closed — is not noticed for half an hour, and until then FishNet reports the client as perfectly connected, so every "are we still connected" test above the transport answers yes. `RaidSession` now calls `Transport.SetTimeout` on both sides from `OnEnable` (`deadPeerTimeout`, seconds — verified applied by reading Tugboat's private `_clientTimeout` in Play mode, because its public `GetTimeout` is hardcoded to return the maximum and tells you nothing). **A graceful close is not a guarantee either**: LiteNetLib's goodbye is one unreliable UDP packet (`NetManager.Stop` → `NetPeer.Shutdown`), so a lost one leaves the peer waiting for the timeout exactly as a killed process does. Both the host and join log lines print it, so a log from a failed run says which value was actually in force. **And even that is not enough**, which is the real lesson: a host tearing its server down **despawns every object first and says goodbye second**, so the reliable despawns arrive while the one unreliable disconnect packet is lost — measured 2026-08-05, the client's avatar, camera and menu all vanished while FishNet went on reporting a healthy connection, and no timeout ever fired. So the last-resort signal is the one that demonstrably does arrive: `LocalAvatar` tells `RaidSession` when **our own** avatar spawns and despawns, and a client that has had none for `orphanTimeout` seconds leaves on its own. Losing your own avatar without asking to is not something that happens in a working raid. **The avatar that never arrived at all is the same dead end and needed its own arming** (added 2026-08-12): that callback only ever fires for an avatar we had, so `RaidSession` also starts the clock from `Update` when it is a client, with no avatar, standing in **any scene but the menu** — the menu is the one scene that spawns none, and naming it rather than naming the level is what keeps the test working once there is more than one location. The direction of that call matters — the level tells the session, never the reverse, so the session layer keeps knowing nothing about the level. **Telling the player why is a stored value, not an event** (`RaidSession.ConsumeNotice`, read by `MenuView.Awake`): the session ends in the hub or in a level and the only thing that can say so is the menu's popup, which does not exist until a scene later — an event fired then is shouted into an empty room, and `MenuView.Awake` calls `ClosePopup` anyway. It is deliberately empty when the player left of their own accord, and `ConnectFailed` is **not** reused for it: that one means an attempt that never landed, and its handler sends you back to the address field. The trade-off is real and is why FishNet's default is what it is: a stall longer than the timeout, such as sitting on a breakpoint, now drops the session. FishNet RPCs apply on the next tick, so a value read in the same frame as the call still shows the old one.

**Sound landed 2026-08-05 and needed no netcode of its own** — that is the rule, not a coincidence: every sound hangs off a state change that is *already* applied on every peer (`Pet.ApplyCarry`/`AnnounceNoticed`, `Door.ApplySwing`, `ShotFlash.ObserversFire`, `PlayerController.State` via `PlayerMotion`, the transform via `NetworkTransform`). If a sound seems to need a new `SyncVar`, it is being hung in the wrong place. `Code/Audio/` holds the footsteps: `FootstepAudio` on both `Player.prefab` and `Old Man.prefab` — **and in neither `LocalAvatar.localOnly` nor `ServerSimulated.serverOnly`**, for exactly the reason `PlayerMotion` exists, since those two lists switch things off precisely on the peers where somebody else's footsteps are supposed to be heard. Pace comes from the transform's own movement on both actors (an agent and a `PlayerController` are each dead on the machines that do not drive them); `PlayerController.State` is asked only for volume. The surface underfoot is a `FootstepSurface` marker found with `GetComponentInParent`, which is why one marker on the root of `HouseOneFloor.prefab` covers all 25 floor tiles and the lawn needs none — the same "the object names its own kind" idiom as `SpawnPoint`. Volumes are **derived from the noise table**, not chosen by ear (`MECHANICS.md` section 2). Old Man is now audible but still emits no game noise. Note `Old Man.prefab` carries **two** `AudioSource`s with different rolloffs — the shot carries across the level, the steps do not — so anything reaching for one must name it rather than call `GetComponent`.

**The scene flow is `Loading` → `Menu` → `Hub` → `Level` → `Hub`** (that is also the order in `EditorBuildSettings`; reworked 2026-08-12, and the scene that used to be `Lobby.unity` is now `Menu.unity` — same GUID, renamed with its `.meta`). `Loading` runs once per launch and is gone. **`Menu` is only the way in**: Host or Connect, and the moment the connection is up the host calls `GoToHub`. A client calls nothing — FishNet sends a newly authenticated connection the global scenes that are already loaded, with the parameters of the load that put them there (`Scened/SceneManager.OnClientAuthenticated`), so it arrives in the hub on its own. **`Hub` is where the session lives** between raids: everyone stands in the saucer, and the host picks a location and flies. Coming back from a raid is `GoToHub` again, which is also how a lost raid is played once more — and because that is a real scene load, everything latched (the outcome, the delivered count, who is dead, which doors are open, where the actors stand) is scene state that `LevelBootstrapper` rebuilds from scratch, so there is no reset code anywhere. The old `Restart`, and with it the trick of loading `Lobby` twice to get round FishNet refusing an already-loaded scene, were **deleted** on 2026-08-12: the hub sits between two raids by construction. Which loader is used is not a detail: **once a session is up, every scene change goes through FishNet's `SceneManager` with `ReplaceOption.All`** (`RaidSession.LoadForEveryone`), because that is what carries the load to every client and keeps spawned objects attached to the right scene — Unity's own `LoadScene` is used **only** when we are not connected to anything (`RaidSession.GoToMenuAlone`, and `HubMenuUI.Fly` on a hub played alone). Pressing Play straight into `Hub` or `Level` skips all of this and is a supported mode, not an accident: `RaidSession.Active` is then null and every caller treats that as "we are alone", not as a failure. `Hub.unity` deliberately carries **no** `Bootstrapper` of its own — the app's one would send it straight back to the menu.

**Every networked scene load carries what the loading screen must wait for in `SceneLoadData.Params.ClientParams`** (one byte, added 2026-08-05). A client never calls `StartRaid` or `GoToHub` itself, so this is the only thing that tells it whether to wait for the menu or for its own avatar. `ClientParams` is the half of `LoadParams` that travels; `ServerParams` beside it is `[NonSerialized]`.

**`Code/UI/LoadingScreen.cs` covers the transitions** — its own `DontDestroyOnLoad` object made by `Bootstrapper` next to the session (its own, because the session prefab is optional). It is **told what to wait for and hides itself**; there is no public `Hide`. Two things only: `Wait.MainMenu` means `MenuView.Current`, not `SceneManager.sceneLoaded`, because FishNet raises `OnLoadStart` even for a scene it then skips as already loaded and no `sceneLoaded` follows; `Wait.AvatarReady` means `RaidSession.LocalAvatarSpawned`, i.e. our avatar, not the scene — the hub and the level both load seconds before the server has finished spawning for everyone, and both are covered by the same value. `Show` refuses to wait for something already true — that is how the screen gets stuck up for good. Its `_stuckTimeout` only uncovers the game and takes **no** decision about the session; `RaidSession`'s own backstops are shorter and win the race. Screen Space – Overlay draws without a camera, which is why it survives the camera-less `Loading` scene and the gap between levels.

**Getting out of a raid is `Code/UI/EndScreenUI.cs`** (added 2026-08-05) — one panel on the avatar's HUD, shown when the raid ends and on `Escape` while it has not, with **В ХАБ** (host only, and only once it is over) and **Leave**. Both sides' Leave is now the same call, `RaidSession.Leave`: host migration does not exist, so a host walking out ends the session and everybody else lands in the menu through their own disconnect. When the raid ends the panel also fills in a three-line summary — animals aboard, survivors, duration — and **counts it once**, because Old Man goes on shooting under an open panel and a survivor count that keeps dropping behind "RAID FAILED" is noise. The duration is the only new replicated value: `RaidState._duration`, written by the server inside `SetOutcome` and measured from `OnStartServer`, since that object's lifetime *is* the raid; `LevelGoal.Duration` mirrors it the way the other four numbers are mirrored, so a level played alone shows a time too. While the panel is up it switches off `PlayerController` and `PlayerInteractor` through its own `suspendWhileOpen` list, and puts back **only what it switched off** — a shot player's controller was already off, and `Resume` must not hand control back to a corpse. The raid itself never stops: three other people are in it. **The outcome is written in exactly one place** — the panel's title. `LevelStatusUI` blanks its own line once `IsWon`/`IsLost` latches, because the panel's background is translucent and the same words underneath read as the text doubling. The server side of somebody leaving already exists and needs nothing new — FishNet despawns the connection's avatar, `LocalAvatar.OnStopClient` calls `LevelBootstrapper.RemovePlayer`, and that routes through `PlayerLife.Kill()` so leaving inside the beam still hands the animal over. **`Cursor.lockState` has exactly three writers — `LocalAvatar`, `EndScreenUI` and `HubMenuUI` — and they are named here; nothing else may touch it.** The rule all three follow is **whatever locks the cursor is what unlocks it, and free is the default when in doubt** — getting that backwards cost two separate bugs on 2026-08-05, a menu with no cursor and a popup that could not be clicked. So `LocalAvatar` locks it in `Apply` and releases it in `OnDestroy` (the avatar can go away with nobody choosing it — the host ends the session, the connection drops, the level reloads — and then no menu ever opened to hand it back), while in the two panels **only closing them re-locks it.** Leaving, flying out, and being disabled with a panel open all hand it back free — what comes next is the menu, the hub or a fresh level, and each either wants a mouse or takes it back itself. `CursorLockMode.Locked` also re-captures on the next click, so a cursor wrongly left locked reads as "it appears and then vanishes when I click". **A dead player watches through `Code/Player/SpectatorCamera.cs`** — it copies a living teammate's `PlayerController.CameraRoot` world transform onto our own in `LateUpdate` (**not** a reparent: the avatar root is scaled `0.1`, the same reason the carried pet is placed rather than parented), `Previous`/`Next` step round the living from `LevelBootstrapper.SensedPlayers`, and both scripts are in `LocalAvatar`'s list so they exist once per screen rather than once per avatar. **`FirstPersonBody` is reversible because of this** (2026-08-05): the camera sits between the eyes, so a spectator must hide the head of whoever they are watching and **put it back** when they switch — a one-way hide leaves that teammate headless for the rest of the raid. It captures the artist's original shadow mode and enabled flag on the first hide, and renderers are local, so hiding a teammate's head here is invisible on their own screen. Neither is in `PlayerLife.disableOnDeath` — measured 2026-08-05, that list is exactly `PlayerController` + `PlayerInteractor`, which is what keeps the camera, the ear and the HUD alive after a death.

**The hub is `Code/Hub/` and `Hub.unity`** (added 2026-08-12, greybox: a `Plane` with its collider, four `PlayerSpawn` markers, a light and a canvas — the saucer has no interior, `UFO.prefab` is exterior only and ProBuilder is not installed). `HubBootstrapper` spawns **one avatar per connection, on that connection's presence in this scene** (`SceneManager.OnClientPresenceChangeEnd`, plus a sweep over whoever is already present in `Awake`) — deliberately *not* `LevelBootstrapper`'s "wait until everybody has the scene", because an avatar belongs to one connection and that is the right moment for it; the same code is also what gives an avatar to somebody who joins while the others are already standing there. `LocalAvatar` registers with both entry points and exactly one of them is ever non-null. `HubMenuUI` is the panel on `Escape`: the host sees the location list (`RaidLocation` = a display name plus a scene name, one entry today, `Level`) and their own address to read out, a client sees "ждём хоста", everybody gets **Выйти**. The choice is not replicated — the host decides and the load is what travels. Late join is open while everybody is in the hub and closed the moment somebody flies (`RaidSession.IsRaidRunning`). `Player.prefab` is used unchanged: `PlayerInteractor`, `LevelStatusUI` and `SpectatorCamera` are already null-safe with no `LevelGoal` and no `LevelBootstrapper`, so nothing needed a hub variant. **`EndScreenUI` was the exception** and now returns early when no goal is bound — otherwise `Escape` in the hub opened its panel *and* the hub's, on one key, with both writing the cursor.

**Actor spawning is the server's since 2026-08-04.** `LevelBootstrapper` lays the level out only where `IsAuthority` holds — the server, or a process with no networking at all, which is what keeps pressing Play straight into `Level` playable. A client creates nothing and receives every actor replicated. Players are one avatar per connection, spawned with `ServerManager.Spawn(avatar, connection)`; **ownership is the answer to "is this one mine"**, applied by `LocalAvatar` (a `NetworkBehaviour`) in `OnStartClient`, which also registers the avatar with `LevelBootstrapper.Current` on every peer. `Player.prefab` carries `NetworkObject` + `NetworkTransform` with `_clientAuthoritative = true` (movement decision of 2026-08-04: the owner moves itself, others interpolate). **The animals and Old Man are the opposite**: `NetworkTransform` with `_clientAuthoritative = false`, spawned by the server with no owner, and a `ServerSimulated` component (`Code/App/`) that switches their `NavMeshAgent` **and** their brain off on every peer that is not the server — an agent integrates locally, so four machines running one would give four different animals. The AI code itself is untouched by the netcode pass on purpose: the gate is a list of references on the prefab, not a branch inside the most tuned code in the project. **The cost of that gate is that everything the gated code produces stops at the machine running it**, and on 2026-08-05 that turned out to be four separate bugs with one shape. Fixed: the animals' and Old Man's animator parameters are set by their brains, so a `NetworkAnimator` (server-authoritative, `_clientAuthoritative = false`) now carries them or they slide about un-animated on every client; a pet's bark is triggered by `PetBrain` and goes out through `Pet.AnnounceNoticed` (an `ObserversRpc` with `RunLocally`), or only the host hears the one warning the other three players need; and the muzzle flash moved out of `OldManBrain` into `Code/OldMan/ShotFlash.cs` for the same reason — until 2026-08-06 that blink was the *only* thing a victim ever saw, and it was lit on the server alone. Since 2026-08-06 the shot is also animated, by IK rather than clips: `Code/OldMan/RifleRig.cs` (a `NetworkBehaviour` beside `ShotFlash`, named `RifleAim` until 2026-08-11) shoulders and aims the rifle at the brain's target while he aims — "aiming + at what point" travels as two SyncVars, and the recoil kick rides `ShotFlash`'s existing RPC, so firing still travels once (`MECHANICS.md` 5.6). **Since 2026-08-11 it also holds the gun the rest of the time**: a second, carry frame hung off the chest bone with both hands pinned to it, blended against the aim frame by the same weight, so the authored floating pose is only what the disabled component restores. Its yaw is negative on purpose — the arms reach `0.465 m` and the grips are `0.34 m` apart, so a barrel pointed straight ahead puts the foregrip out of reach. Also since 2026-08-06 the shot is **dodgeable**: the kill left `OldManBrain.Shoot` and rides `Code/OldMan/ShotPellet.cs`, a plain (non-networked) projectile every peer grows from that same `ShotFlash` RPC — flown from the muzzle toward `RifleRig.AimPoint`, stopped by the sight-blockers mask, armed only where the process decides deaths (`ShotFlash.DecidesHere`, the same formula `PlayerLife` uses), killing through `SensedPlayer.Kill` on impact (`MECHANICS.md` 5.2; a dodged player is re-aimed at next frame, with `shotCooldown` as the pump gap between the two shells — until the magazine runs dry and he stands reloading for `reloadTime`, the guaranteed window after two dodges; all three numbers on `OldManBrain`). **The fourth is the important one and is about the players, not the AI**: see `PlayerMotion` below.

**A remote player was silent and motionless to everyone else, which broke rules rather than looks** (fixed 2026-08-05). `PlayerController` is in `LocalAvatar`'s list, so on every machine but its owner's it is switched off and its `OnDisable` clears `State` and `Speed` — and *three* things read exactly those: `PlayerNoise`, which runs on every avatar everywhere and was therefore emitting `idleNoise`, measured **0** on `Player.prefab` against `walk 25` / `sprint 60`, so on the server every client was perfectly silent and neither Old Man nor the animals could hear one sprint past; `PlayerAnimator`, so teammates slid about standing still; and both brains, through `SensedPlayer`. `Code/Player/PlayerMotion.cs` carries the pair owner → server → everyone and writes it back with `PlayerController.ApplyMotion`, so all three readers keep reading one field and none of them learns whose avatar it is. It is **not** in `LocalAvatar`'s list — it has to run on every peer. Note it sends on change only, which is cheap because `Speed` is quantised by `State`. **Since 2026-08-12 it carries the look pitch as well**, and that one is the project's only value sent at a *rate* (`pitchInterval`) rather than on change — a turning head changes every frame. Nothing in the rules reads it: the reader is the spectator, because the avatar's single `NetworkTransform` is on the root and carries yaw alone, so a dead player used to watch a teammate strictly along the horizon. **The 8 door leaves carry no netcode at all** (reverted 2026-08-05, see the rule below): `Door` is a plain `MonoBehaviour` and the house is plain geometry. The replicated half is `Code/Doors/DoorState.cs`, a `NetworkBehaviour` riding on `RaidState.prefab` — one `SyncList<float>` of target angles, the leaves numbered by a sibling-index path so every machine agrees which entry is which, and a client only sends `RequestUse(index)` while the host re-checks the distance and works the side out from the avatar that connection owns. `Door.Use` falls through to deciding for itself when `DoorState.Current` is null and there is no networking, which is what keeps a level played on its own working; if there **is** networking and the state object has not spawned yet, the use is dropped rather than applied locally.

> **There are no scene `NetworkObject`s in this project, and there must not be.** A scene `NetworkObject` **deactivates its own GameObject** whenever no `NetworkManager` is running (`NetworkObject.TryStartDeactivation`), and FishNet also deactivates them on scene load while it awaits a spawn message. Measured 2026-08-05: a `NetworkObject` on each of the 8 door leaves made FishNet auto-add a ninth to the **root of `HouseOneFloor.prefab`**, so pressing Play straight into `Level` switched the whole house off — no floor, the player fell through — and a client's house stayed off for good. All 9, plus the `EmptyNetworkBehaviour` FishNet had added alongside, were stripped on 2026-08-05 and door state moved to a spawned object. Note also that a scene `NetworkObject` never works without re-saving the scene after adding it: the instances come up with no scene id and `IsSpawned` stays false, which is why the doors appeared to work at all before the strip — they were silently taking their own non-networked branch.
>
> **Do not turn a scene object into a `NetworkBehaviour` if anything else depends on it.** Tried on `LevelGoal` 2026-08-05 and reverted: it shares the scene root `Bootstrapper` with `LevelBootstrapper`, FishNet auto-added a `NetworkObject`, that object came up with `IsSceneObject false` and `ObjectId 65535`, and FishNet **deactivated the whole GameObject** — taking the level's entry point with it. `IsSpawned` also *throws* on a `NetworkBehaviour` whose `NetworkObject` never initialised, so it is not a safe "am I networked" test. The working pattern in this project is `LobbyRoster`: replicated state lives on its **own prefab, spawned by the server**, and the scene object keeps a plain reference to it. That is what `Code/Level/RaidState.cs` + `Content/Shared/RaidState.prefab` now are — the raid's delivered/total/won/lost, spawned by `LevelBootstrapper` on the server, with `LevelGoal` staying a plain `MonoBehaviour` that reads `RaidState.Current` when it exists and its own fields when it does not (a level played on its own). `DoorState` is a second `NetworkBehaviour` on that same prefab rather than a prefab of its own, because it needs spawning at exactly the same moment by exactly the same code. Note the ordering trap: `ServerManager.Spawn` does **not** raise `OnStartClient` in the same frame, so nothing may be written to a just-spawned object on the next line — `LevelGoal` pushes the animal count from `Update` once the object shows up.

**Carrying is replicated through `Pet`** (a `NetworkBehaviour` since 2026-08-05): one `SyncVar<NetworkObject>` naming the carrier's avatar, and every peer runs the existing `ApplyCarry`/`ApplyRelease` from its `OnChange` — the authority included, so there is exactly one path to the picture. A client's `TryTake`/`Release` become `ServerRpc`s that the host re-checks (`CanBeTakenBy` again, and the carrier it has recorded rather than the one the client claims). `ApplyRelease` re-enables the `NavMeshAgent` **only where the animal is simulated**, or a client would start walking an animal of its own against the transform arriving over the wire. Note the idiom for "am I networked" on a component that may also run with no networking at all: cache the `NetworkObject` and ask **it** (`_nob.IsSpawned` / `_nob.IsServerInitialized`) — `NetworkBehaviour.IsSpawned` throws when the behaviour was never initialised.

**Handing an animal over is the server's, and it is not the same event as putting one down** (fixed 2026-08-05). `LevelGoal` is a plain scene component and cannot carry an RPC, so a client's `ReleaseCarried` sends `RaidState.RequestRelease(avatar)` and does nothing locally; the server checks the avatar really belongs to that connection, re-runs `CountsAsDelivery` against **its own** beam test, releases and counts. Before that the client ran the whole method itself — it hid the animal on its own screen, incremented nothing, and the server never heard, which is why only the host could ever deliver. Being aboard then travels as its own `SyncVar<bool>` on `Pet`, because "released" and "delivered" are different states and only one of them takes the animal out of the level.

**Death is replicated too, and for the same class of reason** (fixed 2026-08-05). `PlayerLife` is a `NetworkBehaviour` with one `SyncVar<bool>`; `Kill` is the authority's decision and `ApplyDeath` is what every peer runs. Old Man is `ServerSimulated`, so his shot only ever reaches this component on the server — while it stayed local it broke three things at once, all measured on a build-plus-editor session: a shot client kept playing while the server counted them dead, so Old Man seemed to hear them and never fire; the raid was declared lost the instant the host died, because the server already had nobody living; and the host had no living teammate left to spectate. Note that "who decides" here is asked of the **process** (`InstanceFinder`), not of the object's spawn state — a player leaving is killed on the way out so a beam handover still counts, and by then the object's own answer is already changing.
**`LevelBootstrapper` is the level's entry point** (scene root named `Bootstrapper`, `Assets/_Game/Code/LevelBootstrapper.cs`). It holds every startup reference and, in `Awake`, instantiates the **prefabs** of the player, the three pets and Old Man onto random points of their kind — `seed` on it is `0` for a fresh layout each run, non-zero to repeat one. Actors are reachable through its `Player` / `Pets` / `OldMan` properties; use those instead of searching the scene (`MECHANICS.md` 7.6). **The roster is no longer fixed at `Awake`** (2026-08-04): `AddPlayer(avatar, isLocal)` / `RemovePlayer(avatar)` are the way a player joins or leaves, both brains and `LevelGoal` hold the *live* list rather than a copy, and `RemovePlayer` routes through `PlayerLife.Kill()` so somebody leaving inside the beam still hands their animal over. Drawing the layout and applying it are also split: `ActorSpawner.Draw` is pure and returns point indices (its `Seed` is resolved once and is never zero, so a layout can be named and sent), while `Instantiate` stays in `LevelBootstrapper.Place`. The scale-reference copies of `Dog`, `Kitty`, `Parrot` and `Old Man` that used to sit in a row at `y = 5.58` were removed from the scene on 2026-08-03 — every actor in play now comes from a prefab. The house is furnished from `nappin/HouseInteriorPack` under the scene root `Interior`, grouped per room — the floor plan is 8 spaces on a 2.5 m grid (bathroom, entrance hall, living room, bedroom, kitchen, pantry, kids room, study) plus the corridor spine. Indoor lighting is one realtime point light per interior fixture, all under the scene root `Night Lighting` and named `PL_<Room>_<Fixture>`; the previous house's 17 orphaned lights were removed on 2026-08-03. The entrance hall and the pantry have no lamp prop, so they have no light of their own. Patrol points for Old Man live under the scene root `PatrolPoints` (14 of them as of 2026-08-04; `LevelBootstrapper.patrolRoot` points at it and walks its **direct children in hierarchy order**, so reordering or adding markers reroutes him with no code change — measured 2026-08-04: all 14 on the navmesh, all 182 pairs `PathComplete`). `Player.prefab` carries `PlayerController`, `PlayerInteractor`, `PlayerHands`, `PlayerAnimator`, `PlayerNoise`, `PlayerLife`, `LocalAvatar` and its own camera; **`LocalAvatar` is the ownership gate** (added 2026-08-04) — one list of the components that belong to the person at this screen (camera, `AudioListener`, the HUD canvas, input, the two HUD scripts) plus `FirstPersonBody`, switched on by `LevelBootstrapper.AddPlayer(avatar, isLocal)` for exactly one avatar. `Cursor.lockState` lives there too, because the cursor is one per process and cannot be owned by a component that will exist four times; it animates from `Player.controller` — a base blend tree along **speed in m/s** (idle 0 → `Walk_A` 2.5 → `Run_A` 5) plus a `Carry` layer masked to the upper body by `UpperBody-Mask.asset`, which holds the two carry poses from `Content/Level/Animations` and is faded in by `PlayerAnimator` whenever the hands are full. All of it is humanoid clips retargeted onto the alien, which ships none of its own — **Mixamo files arrive as Generic and must be reimported as Humanoid**, or they silently animate nothing; the 8 door leaves inside `HouseOneFloor.prefab` carry `Door`, so doors open and shut (`Interact`, 90° away from whoever used them — see `MECHANICS.md` 3.8). The pets carry `Pet` (carrier slot and carry speed multiplier), plus `PetBrain` / `PetVoice` / `NavMeshAgent` since block 4; **Old Man carries `NavMeshAgent` + `OldManBrain` since 2026-08-04** — his `Animator` had `applyRootMotion` cleared at the same time, because it shipped `true` and fights the agent for the transform, and his agent's `radius 0.3` / `height 1.8` are deliberately the project's own `Humanoid` agent type (the one the navmesh was baked for), unlike the pets, whose agents are measured off their meshes. He is driven through the vendor controller's bools `Walk 1` / `Run 1` — it has no float speed parameter, and exactly one bool may be true at a time. His muzzle flash is the child `MuzzleFlash`, a point light left disabled until he fires — since 2026-08-06 it hangs on the barrel tip inside `rifle` so it travels with the raised gun, and the shot **is** animated: `RifleRig` does it with IK and no clips (`MECHANICS.md` 5.6), the rifle staying a root child that is *placed* each LateUpdate, the carried-pet idiom — carried at low ready the whole raid, raised to the shoulder only while he aims. For its IK pass he runs the project's own copy of the vendor controller, `_Game/Content/Level/Animations/OldMan-Controller.controller` — identical but for IK Pass on the base layer; the vendor asset is untouched. Both are spawned onto their points at runtime. A carried pet rides one of two anchors on `Player.prefab` — `OverheadAnchor` for the Dog, `FrontAnchor` for the Kitty and the Parrot — chosen by the pet's own `CarryPose`. It is **not** parented to them, because the player root is scaled `0.1` and would shrink it tenfold; it is placed there each frame in `LateUpdate`. The avatar also carries its own HUD (`HUD` canvas inside `Player.prefab`, Screen Space – Overlay): one line in the middle of the screen naming what `Interact` would do — `[E] Open door`, `[E] Grab Kitty` — the pet counter, `YOU DIED`, and (added 2026-08-12) `SpectateHint` at the bottom edge, which names the keys that change who a dead player is watching and appears only while there is more than one living player to switch between. Nothing else about the runtime architecture is settled — do not assume one exists, and do not invent one silently. **FishNet is the chosen netcode library and is installed** since 2026-08-04 (`Packages/manifest.json`, a git URL with no version pin — read the file, and `Library/PackageCache/` for what it actually resolved to). Worth knowing:

- **URP.** Anything shader/material/lighting related must be URP-compatible. There are separate PC and Mobile pipeline assets, both bound in `ProjectSettings/QualitySettings.asset` — a change to rendering usually needs to be made in both. Note that `com.unity.postprocessing` (PPv2) is in the manifest but is Built-in-RP only and must **not** be used: URP post-processing goes through Volume profiles.
  **Grading is per-scene, not global:** the `Level` scene's Global Volume uses its own `Assets/_Game/Content/Level/Surroundings/NightVolume-Profile.asset`. `Assets/Settings/SampleSceneProfile.asset` is still the pipeline default in both RP assets — editing it changes the project-wide default, *not* the level. Edit the scene's own profile to grade the level.
- **Input System package only** (the legacy `Input` API is disabled via `activeInputHandler` in `ProjectSettings/ProjectSettings.asset`, so `Input.GetKey` etc. will not work). Bindings are authored in the `.inputactions` asset. `generateWrapperCode` is **on**, so the wrapper class `InputSystem_Actions` exists at `Assets/InputSystem_Actions.cs` (map `Player`: `Move`, `Look`, `Sprint`, `Crouch`, `Jump`, `Interact`, `Attack`, `Previous`, `Next`) — instantiate it directly, as `PlayerController` does, rather than adding `PlayerInput` components. That generated `.cs` is machine-owned: never hand-edit it, change the asset and let it regenerate.
  **Pointer `Look` delta is already a per-frame increment — never multiply it by `Time.deltaTime`**, or look sensitivity silently becomes frame-rate dependent. The mirror of that rule holds everywhere else, UI included: anything that moves per frame is multiplied by `Time.unscaledDeltaTime` — `LoadingScreen` had a fade and a spinner counted in per-frame steps until 2026-08-05, and both drifted with the frame rate exactly where it is least stable. When such a fix changes a serialized field's **unit**, retune the asset in the same commit or the old number silently means something else.
- **`nappin/HouseInteriorPack` is not authored at real-world scale, and not uniformly so** — `Fridge` comes in 3.69 m tall, `Wardrobe` 3.78 m, `SingleBed` 2.81 m (taller than the 2.5 m walls), while `BedsideTable` is only 0.39 m and needs scaling *up*. There is no single pack-wide factor: each item is scaled individually against a real reference height, with Old Man (1.79 m) as the yardstick. Several prefabs also ship with doors modelled *open* (`Fridge`, `Wardrobe`, `KitchenSink`, `Storage1`, `Drawer2`), which inflates their footprint and eats navmesh — close them before placing. **Every item also ships as one `BoxCollider` running from the floor to its very top**, so nothing in this house has a space under it until somebody cuts one: on 2026-08-11 the coffee table, the two dining chairs, the study chair and the dining table inside `HouseOneFloor.prefab` had that box shrunk to the tabletop (the seat, on chairs) with the legs and backrests added back as **extra `BoxCollider`s on the same GameObject** — no new objects, and the pack itself is untouched. The gaps that opened are measured in `MECHANICS.md` 3.1; the `Desk` was left alone because its drawer pedestal is full height.
- **`Player.prefab` has root scale `0.1`** (the alien is 0.5 m tall), so Unity's defaults, which assume a 2 m human, are wrong here — and components mix local and world units. `CharacterController.height`/`radius`/`center` and any `localPosition` scale with the transform; `stepOffset` and `skinWidth` are in world metres and do not. Before adding a component to a scaled prefab, check which space each field is in — the table in `MECHANICS.md` section 2 records the ones already resolved. **Crouch is a real size since 2026-08-11**: `PlayerController` shrinks the capsule from `0.5 m` to `0.26 m` and lowers the camera with it, refuses to stand up when `OverlapCapsule` finds a ceiling, and reads the button rather than `State` (which is `Idle` whenever the player is not moving). The standing height, centre and eye are captured from the prefab in `Awake` — only the crouched height is a tunable. **Crouching and carrying exclude each other, both ways** (2026-08-11): full hands ignore the crouch button and `Pet.CanBeTakenBy` refuses a crouched player, which is what makes "crouched with an animal" unreachable — the two carry anchors are plain children of the root beside `CameraRoot` and do not drop, so a crouched carrier would hold the Dog inside the tabletop they crawled under. That ceiling test also skips colliders whose root has a `PlayerController`: avatars share the `Default` layer with the house, so without it a teammate standing against you silently forbade standing up. `PlayerMotion` carries the flag to the other peers, because `SensedPlayer.AimPoint` is the capsule's centre and a remote avatar's controller is switched off.
- **AI Navigation (`com.unity.ai.navigation`) is installed and in use** — the level's NavMesh is baked through it (see *Current state*). Use it for pet flee/hide and Old Man movement rather than hand-rolling pathfinding.
  **The agent type is a project-wide setting, not a surface setting.** A `NavMeshSurface` only references it by `agentTypeID`, so a bad agent type silently breaks every bake and reads as "the navmesh ignores walls". Values live in `ProjectSettings/NavMeshAreas.asset`, edited via `Window → AI → Navigation → Agents`; there is exactly one type, `Humanoid`, and its radius is sized to the house's narrowest doorway. Read the file before changing anything navigation-related.
  **In this house the visible floor and the collidable floor are different objects.** Every floor module carries `Interior_Floor` (mesh **and** `BoxCollider`, layer `WalkingArea`, `y −0.10…0.10`) plus `Interior_Floor_Up` — a zero-thickness mesh with no collider that just draws the top surface. One tile in the entrance hall, `Floor_0/Floor/Floor2 (5)/Interior_Floor_Up (1)`, shipped without its collidered twin: the floor was visible but not solid, so the player walked in and dropped 10 cm onto the lawn plane that runs under the whole house. Fixed 2026-08-03 by giving that tile the same `BoxCollider` and the `WalkingArea` layer. The way to find this class of bug is a grid of downward raycasts compared against the floor renderers — "visible but not solid" cells; it is invisible in the scene view.
  **Bakes are driven by `Include Layers`, not by static flags** — an object outside the mask does not exist for the bake, so it neither blocks nor creates walkable floor. The three pets sit on their own `Pet` layer, added 2026-08-03 so the interaction search can run every frame with a mask: unmasked, that query returns up to 59 colliders in a furnished room, masked it returns at most three. Layer assignment for the house lives in `HouseOneFloor.prefab`: floor on `WalkingArea`, all structural pieces on `BlockedArea`, the 8 door leaves on `Door` (deliberately outside the mask so the navmesh runs through every doorway, while still blocking the player physically). Because of that, a shut door stops the player but **not** a `NavMeshAgent` — AI that must respect doors reads `Door.IsOpen` (`MECHANICS.md` 4.6), it cannot rely on the navmesh.
  Removing a `NavMeshSurface` component **deletes its baked `NavMeshData` asset** — the package does this in `NavMeshAssetManager`, without a prompt.
- **The alien's own avatar does not fit the alien's own prefab — we build our own.** `Model.fbx` names its bones `mixamorig:Hips`, `mixamorig:LeftUpLeg`, … and `ModelAvatar` is built for those names, but the vendor prefab `CuteAlien.prefab` (the ancestor of our `Player.prefab`) renames them to `Hips`, `LeftUpLeg`, … — so the humanoid avatar binds to nothing and **no animation is applied at all**, silently. Measured 2026-08-03: `Animator.GetBoneTransform(Hips)` returned null even with `AlwaysAnimate`. The fix in this project is `Assets/_Game/Content/Level/Player/Player-Avatar.asset`, built with `AvatarBuilder.BuildHumanAvatar` against the renamed skeleton and assigned to `Player.prefab`. Three traps came with it. A humanoid bone's name **must be unique in the whole hierarchy** (the mesh object `Head` had to be renamed to `HeadMesh`, or the build fails with "Ambiguous Transform"). `AvatarBuilder` reports failure only through `avatar.isValid`, with the real reason in the console. And **the skeleton must be described unscaled**: the first `SkeletonBone` entry is the root, and putting the prefab's own `0.1` scale in it makes Unity mis-measure the character — every retargeted pose then sat `0.10 m` too low and the model walked knee-deep in the floor (measured 2026-08-03: feet at `−0.09` instead of `+0.011`). Build the avatar from a probe whose root scale is `1`; the prefab keeps its `0.1` on top. If bones are ever renamed or the rig re-proportioned, rebuild that asset and re-measure the feet.
- **Almost the whole house is marked Static — anything that has to move must be cleared first.** 901 of `HouseOneFloor`'s 949 objects carry `Everything` static flags. A **Batching Static** renderer is merged into a combined mesh when Play mode starts and then ignores its transform: the object still moves for physics, but the visible geometry stays put. That is how `Corner_3B/Exterior_Door` behaved on 2026-08-03 — measured in Play mode, its collider swung `0.776 m` while its renderer moved `0.000 m`, so the door was open but looked shut. Clearing the flags on the leaf and its five children fixed it. Before animating anything inside the house, check `GameObjectUtility.GetStaticEditorFlags`.
- **An unfocused editor does not simulate.** With the OS focus elsewhere (e.g. on a chat window driving the editor over MCP), play mode freezes entirely — `Time.time` stands still and nothing moves, which reads as impossible teleports and vanished states between two tool calls. For any MCP-driven play-mode measurement, set `Application.runInBackground = true` first (runtime-only, resets with play mode); discovered at the cost of half an hour on 2026-08-06.
- **Git LFS is active** (`.gitattributes` routes models, textures, audio and other binaries through it). Keep new binary assets under the existing LFS rules rather than adding patterns ad hoc.
- **Unity YAML merges are probably *not* protected.** `.gitattributes` asks for `merge=unityyamlmerge`, but the driver itself is a local git-config setting that isn't versioned — and it was absent in every scope on this machine as of 2026-08-01. Check with `git config --get merge.unityyamlmerge.driver`; empty means git falls back to a plain text merge on `.unity`/`.prefab`/`.asset`, which corrupts them. Avoid situations that merge scene/prefab changes; if one is unavoidable, say so and let the user resolve it in the editor.

## Working rules

These are load-bearing. Keep them in force even when the task is small.
- **For codestyle use `CODESTYLE.md`
- **Don't commit stuff to git.** User can make a commit on his own after they check out your work.
- **Don't write extensive comments in code.** Use short technical vocabulary and use it only in places where those commentaries are absolutly necessary for understanding code. if a method is called GetPlayersCount and returns players count - it's obvious what it does. Only some hardcoded complicated logic requires descriptions on how it works. This **overrides** "match the surrounding style": much of the existing code carries long narrative comments and XML docs written before this rule — do not copy that density when editing those files, and don't rewrite the old ones either unless the code under them changes.
  - **One or two lines.** A comment states the non-obvious constraint or the measurement, not the story around it. No dates, no bug retellings, no "this used to be X" — that history belongs in `CLAUDE.md` or the design docs.
  - **Only where the code cannot say it**: a magic number's origin, an ordering that looks arbitrary, an API trap (Unity fake-null, undefined `RaycastNonAlloc` order). Never a paraphrase of the next line.
  - **Same for `[Tooltip]` and XML docs.** A tooltip is a field label with its unit — one sentence, two at most. `<summary>` says what the type is for, not why it was written.
- **Do exactly what's asked — then stop and report.** Not a partial version, not a souped-up version with extra "fixes", restarts, or refactors that weren't requested. If ambiguous, ask instead of assuming.
- **Never guess or speculate.** Don't theorize about what the code does or why something breaks — open the file and verify. For tuned systems, where the behaviour comes from the numbers rather than the structure, this is the whole job: read the actual values and the comments around them before changing a tunable, and change one at a time.
- **Never lie or invent.** If you don't know something, say so. When your tools or knowledge aren't enough to finish the task, stop and tell the user exactly what you're missing and what you need from them (a file, a credential, a decision, editor access). If the gap is factual or external (an API, a Unity/C# detail, a package behaviour), use web search to find a real source rather than answering from memory — and cite it.
- **Irreversible / external actions require explicit approval.** `git push`, publishing, deleting or overwriting files you didn't create, force operations — explain what you're about to do and wait for a "yes". Reading is always fine.
- **Data safety for assets.** Never delete or rename an asset without its `.meta` file (renaming the pair together preserves the GUID; losing the `.meta` breaks every reference to it). Don't hand-edit scene/prefab YAML unless you know the format — the scene and the `Level/` prefabs are hand-built in the editor and are the least recoverable thing in the repo. Don't edit anything inside a vendor pack folder. Explain and get approval before any bulk asset operation.
- **Commit after each logical unit of work.** Stage the relevant files by name — including the `.meta` files — and commit once a feature/fix/refactor is complete; split unrelated changes into separate commits. Don't commit mid-flight or mix unrelated edits.
- **Self-check before reporting "done".** At minimum: the change compiles against the real Unity/C# API; Unity lifecycle patterns are preserved — including the fake-null gotcha, where a destroyed `UnityEngine.Object` compares `== null` but is not a real null, so `?.` and `??` lie about it (use plain `== null` / `if (obj)` on Unity objects); and the change actually does what was asked. This editor can't be run from here — runtime behaviour has to be verified by the user in Play mode, so say that rather than claiming it "works".
- **Keep this doc current, in the same commit.** After any change to architecture, project structure, conventions, or the game design above, update `CLAUDE.md` alongside the code. It's the source of truth for the next conversation.
- **Write the minimum that works.** Before adding code, walk this ladder and stop at the first hit:
  1. Does this need to exist? → if no, skip it (YAGNI).
  2. Already in this codebase? → reuse it, don't rewrite.
  3. Does the C#/.NET standard library do it? → use it.
  4. Native Unity feature (engine API, package, editor tooling)? → use it.
  5. An already-installed package (`Packages/manifest.json`)? → use it.
  6. One line? → one line.
  7. Only then: write the minimum that works.

  Justify any new dependency, and modify as little existing code as possible.
